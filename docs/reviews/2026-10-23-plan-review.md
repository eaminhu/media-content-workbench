# 实施计划审阅记录

日期：2026-10-23
审阅范围：此前完整对话、README.md、docs/superpowers/plans/2026-10-23-media-content-workbench.md，以及 OpenAI 官方 API 文档。
结论：独立网页、服务端调用 GPT、按步骤使用 skills 的总体方向成立。原计划是初稿，存在流程遗漏、技术选择缺少依据和运行机制缺失，完成以下修订后再作为实施基线。本记录提出修订建议，不将新的产品取舍视为已获用户确认。

## 1. 流程缺少正文与逐页文案生成（高优先级）

原计划第 23—29 行从选题打磨直接进入自然语言优化和做图。topic_polish 的定义只改进选题，没有明确产生正文、页序和逐页文字的环节；校正也缺少可核对的文案基线。

建议明确以下依赖关系：
选题池 → 选题评测 → 资料研究 → 大纲/页序 → 正文或逐页文案 → 内容评测与打磨 → 自然语言优化 → 文案确认 → 绘图方案 → 做图 → 校正 → 导出。
复盘从已发布内容读取数据，再反馈到选题池。界面可以把相邻步骤放在同一工作区，不必把每个内部动作都做成新页面。用户可以导入已有稿件并从中间进入，前提是提供该步骤需要的输入。

验收：从一句主题出发，可以产生可读稿件；从已有稿件进入，也能继续完成图卡。不能把缺少正文的选题直接交给图片生成。

## 2. “选题复盘”的含义与首版范围需要确认（产品选择）

原计划第 27、71、104 行把复盘全部解释成发布后的指标分析，但用户没有明确这一含义。它也可能指创作前再次检查选题是否成立、创作完成后的内容质量复盘。

修订时把选题复审和发布复盘作为不同操作：
- 选题复审：核对读者问题、事实证据、角度、重复程度和预期价值。
- 发布复盘：使用同一发布时间窗口的真实数据，区分观察、推测和下一轮试验；缺失不是零。

同时，单用户、小红书默认、PostgreSQL 和对象存储都是原计划提出的方案，不是用户已逐项确定的需求。先标明这些假设，避免把通用自媒体工作台固化成单平台科普工具。

## 3. API 方案出现未经说明的切换（高优先级）

此前对话最后推荐 Responses API 按步骤调用，落盘计划第 7、9、75—84 行却固定为 Agents API，缺少切换理由和最小验证。

已核实的官方事实：
- Responses API 的 shell 工具和 Agents API 沙箱均能使用 Agent Skills，二者加载机制不同。
- Agents API 的能力目录位于执行环境中，相关目录要先存在；把网站本机路径写进请求并不代表云端能够读取。
- Agents API 快速入门使用 Beta 命名空间和 Beta 请求头，并要求 API 项目权限；目前尚未核实本项目账户的实际可用性。

建议在实施开头增加技术验证关口：
1. 使用一个实际 skill 和一条已有输入，验证加载、必要参考文件、工具调用、结构化输出和结果保存。
2. 记录所用 API、模型、skill 文件哈希、运行环境、耗时、实际用量和失败恢复结果。
3. 据此记录技术决策，说明选择哪条路线、运行在哪里、哪些工具由网站提供。
4. 不把“读取 Markdown 并拼进提示词”写成已经保留原有 skill 执行行为；这种方案属于适配方案，需要明确质量差异并获得认可。

这一关口需要实际 API 凭据与授权的调用预算；本次仅审阅文档，没有发起收费调用。

## 4. 后台任务缺少实际执行者（高优先级）

原计划第 86—95 行定义 queued、running、succeeded、failed，但没有定义谁消费队列、如何在网页关闭或服务重启后继续追踪。仅保存状态和前端轮询不能保证任务执行。

修订要求：
- 提交接口持久化任务并返回 runId；独立 worker 领取任务并保存外部请求/session ID。
- 明确领取锁、心跳、超时、任务租约和服务重启后的对账过程。
- 提交结果不明确时先查询外部运行状态，避免盲目重试造成重复出图和收费。
- 取消状态区分“已请求取消”和“外部执行已停止”；关闭网页不表示任务取消。
- 结果采用、回调处理和重复事件都应有幂等保护，失败原因与业务输出分开保存。

新增计划文件职责：src/worker.ts（任务消费）、src/lib/jobs/（领取/恢复）、src/lib/openai/events.ts（外部事件对账）。具体队列方式在部署方式确定后选择，不先堆叠多个队列组件。

## 5. 版本记录和步骤依赖没有落到数据模型（高优先级）

原计划第 31、68、94、103 行承诺版本保存和回退，但 Topic 只有当前版本号，缺少版本内容、采用状态、来源运行和依赖关系。WorkflowRun 的 JSON 也不能独自表达用户手改后的确认稿。

修订要求：
- 增加不可变的 ContentVersion，记录内容、父版本、作者类型、来源运行、创建时间和采用状态。
- 分开表达候选选题与确定制作的一期内容；账号/系列配置与单期内容分层保存。
- WorkflowRun 固定引用输入版本，不在运行中读取随时变化的“最新稿”。
- 图片记录 pageId、提示词版本、文案版本、参考图和生成参数。
- 上游修改后，下游结果标记“依据旧版本生成”，由用户选择保留或重跑。
- 回退通过重新采用旧版本完成，不删除历史。任何清理/删除功能另按用户的删除确认规则设计。

具体值追踪：文案 v3 → 第 2 页提示词 p2-v1 → 图片 a2-v1 → 校正报告 r1。文案变为 v4 时，a2-v1 与 r1 仍引用 v3；界面提示它们需要复核。

## 6. 缺少判断“效果好”的基准（高优先级）

用户提出此项目的依据是过去做过效果满意的内容。原计划只验证 API 成功和页面可操作，没有证明迁移后保留已有质量。

修订要求：
- 从用户已经认可的历史作品中建立基准；本地多米诺效应示例只能作为候选，不能自动当作认可样本。
- 固定评分维度、分值含义、各档描述和适用范围；每个评分附证据和具体修改建议。
- 不用“模型给自己高分”作为通过依据；内容打磨后重新核对事实、约束和原意。
- 为同一输入保存原流程结果和新网站结果，按事实准确、完整性、读者可读性、作者语气、图片文字和版式逐项比较。
- 选择有代表性的正常输入、信息不足、存在事实错误、修改指定页面、生成中断等场景进行端到端验收。
- 给出可记录的验收条件：无关键事实被无提示改动；已确认要求保留；评分理由可追溯；错误明确显示；成功页不会因重试被覆盖。

## 7. 资料研究、事实来源和历史避重缺失

原计划选题输出有“事实待查项”，但没有研究动作、来源记录或事实核查数据。已盘点的技能包含资料核查与避重，这些能力在原计划里遗漏。

增加 SourceEvidence：URL、标题、访问日期、支撑的论断、原文位置/必要摘录、已核实状态。把事实来源关联到正文和校正问题。无法核实的论断显式标记，不因为模型措辞流畅就视为正确。
已有作品需要支持导入或录入，并参与选题相似性比较；语义判断应解释相似之处和新角度，不能只用关键词黑名单。

## 8. 用户打磨与做图的交互粒度不足

每个步骤除按钮外，还需有自然语言补充要求、目标页选择、保留条件与版本对照。例如“只改第 3 页，保留已经确认的标题”应直接限定本次运行。
做图应先提供页序和提示词预览，再生成封面/样张确定风格，随后生成其余页；支持单页重做与局部失败恢复。校正建议返回后可编辑和采用，无需在只读检查开始前再机械增加一次确认。

先做可操作的工作台界面草图，验证选题比较、改稿、采用版本和单页重做的路径。最终导出至少包含图片、顺序、标题、正文、标签和必要来源说明。

## 9. 费用与实施依赖需要前移

原计划把用量/成本记录和访问控制放到最后，实际第一次 API 调用前就需要基本保护。
先确定本机私用还是部署后跨设备访问，再选择数据库、对象存储和 worker 部署。不要因为“独立网页”就直接等同于“必须立即上云”。
调用前设置用户认可的单次/每日上限与出图张数；保存供应商实际用量，无法精确获知费用时明确显示估算。ChatGPT 订阅不能视为 API 预算已配置。
继续实施时，包安装仍需按用户规则单独获得明确确认；本次文档审阅不涉及安装、Git 操作、密钥创建、部署或 API 调用。

## 建议重新安排的交付顺序

1. 明确第一类内容、复盘含义、部署方式，收集认可的历史样本。
2. 写流程依赖和输入/输出契约，完成可操作界面草图。
3. 用一个 skill 打通“网页提交 → 后台运行 → 真实 GPT 结果 → 保存 → 刷新恢复”。
4. 补齐文案生成、打磨、自然语言优化、版本采用、资料来源和失效提示。
5. 接入单页图片生成与校正，再扩展整套图卡与导出。
6. 接入发布复盘、历史避重、长期统计和正式部署。

技术选型和扩展功能由前面关口的证据支撑，避免一次性迁移所有 skills 后才发现质量或运行方式不适合。
